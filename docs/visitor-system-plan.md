# Visitor System — 第一版需求与实施计划

日期：2026-10-04  
状态：核心业务需求已讨论确认；文中标注的建议与待验证项不代表已确认需求。  
产品语言：英文；本文使用中文说明。

实施现状（2026-10-04）：访客三步签到、邮箱签离、协议快照、签名/照片采集、管理员授权的证据查看，以及访客和受访员工通知已接入。Azure PostgreSQL 已应用 `20261005000000_visitor_checkin_evidence` 迁移。签名和照片当前保存在运行本地应用的项目目录 `.visitor-files`；部署到多实例或云端前，必须迁移到私有、持久化的文件存储。实际平板/手机相机测试、Brother 打印、队列式邮件投递、导出和记录清理仍待完成。

## 1. 产品目标与部署

为公司提供简单的访客自助登记系统。访客到场后使用前台平板或扫描二维码使用自己的手机签到，无需预约。

- 使用同一套应用代码，每家公司单独部署，使用独立 PostgreSQL 数据库。
- 第一版不实现多租户平台；公司内部支持多个账号和三个角色。
- 公司资料、部门、访问目的、协议、SMTP 和打印设置由管理员配置，不写死在代码里。
- 前台平板启动进入 Kiosk Mode；后台由管理员、前台和员工在自己的电脑上访问。

## 2. 技术栈

| 层 | 方案 |
|---|---|
| 前端 | Next.js App Router、TypeScript |
| 服务端 | Node.js、Next.js Server Actions / Route Handlers |
| 数据库 | PostgreSQL |
| 数据访问 | Prisma ORM 7 |
| PostgreSQL 驱动 | pg、@prisma/adapter-pg |
| 数据库版本管理 | Prisma Migrate |
| 开发数据查看 | Prisma Studio，不作为产品管理后台 |

建议照片和签名文件放在受控文件存储中，数据库保存文件引用。具体存储与部署方式在实施前确定。

## 3. 访客签到

### 3.1 平板首页

显示公司品牌信息及以下入口：

- `Check In`
- `Check Out`
- `Print Badge`，供手机签到的访客取胸牌或重试打印。
- 手机登记二维码，打开本公司的访客登记页面。

建议完成或取消登记后清空表单并返回首页；闲置表单超时清空，避免下一位访客看到个人信息。真正的设备开机启动及锁定退出由设备配置配合实现，网页本身不等于操作系统的 Kiosk 锁定。

### 3.2 Step 1 — Your Details

| 英文字段 | 规则 |
|---|---|
| Full Name | 必填 |
| Company Name | 公司来访必填；个人来访选择 Personal Visit |
| Email | 必填 |
| Phone Number | 必填 |
| Vehicle Registration Number | 开车来访时必填，否则不适用 |

建议提供是否开车的选择，用于决定车牌输入框是否显示。点击 `Next` 进入下一页，个人信息与访问信息不放在同一页。

### 3.3 Step 2 — Visit Details

- `Person to Visit`：输入员工 First Name 或 Last Name 搜索，选择受访人。
- 仅显示可接待访客的有效员工；离职停用账号不显示。
- `Purpose of Visit`：下拉选择，选项由管理员维护。
- 搜不到受访人时提示：`Person not found. Please ask reception for assistance.`
- 前台可代填登记信息，但不能代访客签名或使用代替访客的照片。

建议搜索结果显示姓名和部门，避免同名混淆。受访人根本不在员工名单时如何处理，以及前台如何将代填表单交给访客签名拍照，列为实施前待确认项。

### 3.4 Agreement 与 Photo

- 显示本公司配置的协议内容，访客手写签名。
- 使用平板前置摄像头拍照；手机使用自身摄像头。
- 允许预览、重拍并确认照片。
- 最终提交后完成签到，记录实际提交成功时间。

建议保存每次签署的协议快照或不可变版本、签名及签署时间，后续协议修改不改变旧记录。协议、签名、拍照的详细页面布局与相机不可用时的处理仍需确定。

### 3.5 成功与后续处理

签到记录保存成功即算签到完成；邮件发送或胸牌打印失败不影响签到结果，不要求访客重新登记。

- 给访客发送签到确认：公司名称、受访人、签到时间。
- 给受访人发送到访通知：访客姓名、公司、访问目的。
- 照片不作为邮件附件。
- 平板签到后按打印设置发起打印；手机签到后提示到平板打印。

手机成功提示：`Check-in complete. Please collect your visitor badge at the reception tablet.`

建议签到与待发送通知在同一数据库事务中持久化，由后台任务发送并记录结果；重复点击提交不得生成重复签到。邮件重试不得生成新访问记录。

## 4. 胸牌打印

- 使用 Brother 无线标签打印机。
- 只打印访客姓名和公司名称，不打印照片。
- 手机签到访客在平板点击 `Print Badge`，输入 Email，查找最近一次签到；自助打印仅限公司当地日期的当天记录。
- 不重复登记。打印失败可重试，或请前台协助补打。
- 失败提示：`Unable to print your badge. Please try again or ask reception for assistance.`

建议个人访客公司名称位置显示 `Personal`；打印开关、标签尺寸和布局由后台配置。

**待验证：**无线连接不等于浏览器能够直接自动打印。取得 Brother 具体型号和标签尺寸后，验证官方 SDK、打印服务或本地打印桥接方案，以及平板兼容性。云端应用不能默认直接访问前台局域网打印机。打印适配应独立封装，打印任务状态与签到状态分开保存；无法确认实际出纸时不标记为已完成。

## 5. Check Out

- 自愿签离，访客可以直接离开。
- 输入 Email，按签到时间查找该邮箱最近一次访问记录，不限当天。
- 最近一次未签离：更新该记录的离开时间。
- 最近一次已签离：提示 `Already checked out`，不回退修改更早的记录。
- 旧的未签离记录不动，不自动补离开时间。
- 未签离显示 `Not Checked Out`，不能据此宣称访客仍在公司。

建议邮箱匹配不区分大小写、忽略首尾空格。公开页面只返回操作所需信息，不展示历史记录列表或照片。

## 6. 账号与权限

三个角色共用一套后台，服务端检查权限；员工的数据查询必须限制到自己作为受访人的记录。

| 功能 | Administrator | Receptionist | Employee |
|---|---|---|---|
| 登录后台 | 是 | 是 | 是 |
| 访问记录范围 | 全部 | 全部 | 仅自己的受访记录 |
| 公司配置、账号与员工管理 | 是 | 否，建议 | 否 |
| 协助登记、补签离、补打胸牌 | 是 | 是 | 否，建议 |
| 手动清理记录 | 是 | 否，建议 | 否，建议 |
| Excel 导出 | 是 | 待确认 | 待确认 |

角色已确认；标注建议或待确认的具体权限在实现前定稿。Receptionist 可不配置，无前台账号时由 Administrator 处理接待。

### 6.1 初始化与登录

- 首次使用设置第一个管理员账号和密码。
- 统一 Email + Password 登录，支持邮件重置密码。
- 管理员可以修改自己的账号信息和密码。

建议初始化仅能成功一次，并由部署时的一次性凭据保护；初始化完成后关闭该入口，避免公开部署被他人抢先注册。更改登录邮箱、重置密码和 SMTP 的操作需要适当的身份验证。

### 6.2 邀请与员工资料

管理员输入邮箱并指定 Receptionist 或 Employee → 发送邀请 → 接受邀请、设置密码 → 登录完善个人信息。

- 员工填写 First Name、Last Name，从配置列表选择 Department。
- 建议资料完整后才出现在受访人搜索中。
- 邀请与重置密码链接应有有效期且只能使用一次；支持重新邀请。
- 员工离职后 Deactivate：禁止登录、从受访人搜索移除，历史受访记录保留。

## 7. Configuration

| 配置模块 | 内容 |
|---|---|
| Company Settings | 公司名称、Logo、地址、时区 |
| Departments | 添加、修改、停用部门 |
| Visit Purposes | 添加、修改、停用访问目的 |
| Agreement Template | 公司自己的协议内容 |
| SMTP Settings | SMTP Host、Port、TLS、Username、Password、Sender Name、Sender Email |
| Printer Settings | 打印开关、设备连接配置、标签尺寸与布局 |

字段细节为建议实施方案。默认部门和访问目的仅作为可编辑的初始化数据，不作为代码内固定业务规则。

建议 SMTP 密码加密保存，不返回明文，提供 `Send Test Email`；加密密钥由部署环境提供，不与密文存放在一起。首次 SMTP 尚未配置时应明确提示邀请与通知不可发送。配置修改应保留历史记录当时的公司名称、部门、访问目的等必要快照。

## 8. 记录管理与 Excel

- 长期保存访客记录、照片和签名，不自动过期删除。
- 管理员需要时手动清理。
- 后台支持记录列表、详情、日期筛选与搜索。
- Excel 格式为 `.xlsx`，包含姓名、公司或个人来访、Email、电话、车牌、受访人、访问目的、签到与签离时间；照片不嵌入 Excel。
- Dashboard 建议显示今日签到数量和未签离数量，未签离不等同于实际在场人数。

建议清理前显示数量、明确确认，并同步清理对应照片与签名；保留必要操作日志。具体删除范围和恢复策略待确认。导出将用户输入作为文字处理，避免被 Excel 解释为公式。

## 9. 数据模型规划

现有 schema 是初稿，不能直接当作最终模型迁移。

| 实体 | 用途 |
|---|---|
| User | 邮箱、密码哈希、角色、账号状态、姓名、部门 |
| Department | 可配置部门、有效状态 |
| Invitation / PasswordResetToken | 邀请、密码重置、有效期与使用状态 |
| CompanySettings | 公司信息与时区 |
| VisitPurpose | 可配置访问目的 |
| AgreementVersion | 协议内容与版本，建议 |
| VisitRecord | 每次访问的信息快照、受访人、签名和照片引用、签到与签离时间 |
| EmailJob / PrintJob | 后续处理任务、结果与失败原因，建议 |
| OperationLog | 配置、账号、补签离、清理等关键操作 |

第一版可以直接以每次 VisitRecord 保存访客信息，不强制创建长期 Visitor 主档，避免根据邮箱误合并不同人的信息。是否保留独立 Visitor 表在 schema 设计时评估。

- 删除 VisitAppointment、预约审批和预约二维码关系。
- 最初的 BlackList 尚未确认，不列为第一版必做。
- PostgreSQL JSONB 在 Prisma 中使用 `Json @db.JsonB`，不是 `Jsonb` 类型。
- Prisma 7 连接 URL 放在 `prisma.config.ts` 中；运行时客户端使用 PostgreSQL adapter。
- 建议采用 Prisma 7 的 `prisma-client` generator，指定输出目录；服务端复用客户端实例。
- 时间统一存储为 UTC，按公司时区显示、筛选和判断当天。
- 附件和密码不进入日志；照片、签名的读取必须检查权限。

## 10. 实施顺序与验收

### 阶段 1：基础与数据库

建立 Next.js 项目、Prisma 7 配置、模型和首次迁移；完成初始化管理员、登录、角色权限。确定照片存储、HTTPS 与部署方式，同时尽早验证 Brother 打印接入，避免最后才发现设备限制。

验收：初始化只能完成一次；三个角色的数据访问范围正确；可以备份并恢复数据库和照片文件。

### 阶段 2：配置与账号

实现公司资料、部门、访问目的、协议、SMTP，以及账号邀请、资料完善、账号停用。

验收：修改配置无需发布代码；员工接受邀请后完善资料；停用后无法登录或被搜索，旧记录保留。

### 阶段 3：签到闭环

实现 Kiosk 和手机响应式表单、二维码、受访人搜索、手写签名、拍照与签到保存。

验收：个人来访、车牌条件必填、找不到受访人等分支可用；重复提交不重复登记；签名和照片关联到正确访问记录；下一位访客不能看到上一位信息。

### 阶段 4：通知与胸牌

实现 SMTP 通知、Brother 打印适配、手机签到后取胸牌、失败提示和前台补打。

验收：邮件或打印失败不影响签到；手机访客无需重复登记即可取胸牌；贴纸只有姓名和公司名称。

### 阶段 5：签离与后台记录

实现邮箱查找最近访问的 Check Out、后台记录与详情、Excel 导出和管理员清理。

验收：签离不修改旧记录，不自动补时间；Excel 包含所需字段；权限检查覆盖导出、附件和删除接口。

### 阶段 6：现场试用与交付

在实际平板、手机和 Brother 打印机上走通全流程，包括断网、相机拒绝授权、SMTP 失败、打印机离线和重复操作。提供配置说明、启动与备份说明。

## 11. 实施前需要定稿的少量细节

这些不妨碍形成计划，不扩大产品范围：

1. Brother 型号、标签尺寸、现场网络及实际打印接入方案。
2. Receptionist / Employee 的导出权限、照片和签名可见范围。
3. 前台代填后交给访客签名拍照的操作方式；受访人不在名单时如何补录或处理。
4. 首次协议内容由客户提供还是提供示例；保留签署时版本的实现。
5. 部署、文件存储、备份恢复，以及相机不能使用时的处理。
6. 记录清理范围、操作确认和关联文件处理。

## 12. 第一版不包含

提前预约、审批、共享多租户平台、门禁硬件、人脸识别、短信服务及未确认的黑名单功能。

本计划同时作为第一版验收清单。当前本地应用和 Azure 数据库已有部分实现；现场设备验证和正式部署仍未完成。
